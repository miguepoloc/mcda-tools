# Contributing to MCDA Tools

Thank you for your interest in contributing to **MCDA Tools**! We welcome bug reports, algorithm suggestions, feature improvements, and pull requests from researchers, educators, and software engineers.

---

## Code of Conduct

We are committed to providing a welcoming, inclusive, and harassment-free environment for everyone. Please be respectful and constructive in all issues, discussions, and code reviews.

---

## Reporting Bugs and Inconsistencies

Numerical accuracy and algorithm consistency are fundamental to this project:

1. **Check Existing Issues**: Please search the issue tracker before opening a new issue.
2. **Detailed Reproduction**: Include:
   - Specific method or feature used (e.g., AHP, VIKOR, Spatial Geovisor).
   - Input data (exact judgment matrix, criteria weights, decision matrix values, or layer configuration).
   - Expected output vs. actual output (including mathematical rationale or academic references).
   - Browser / OS environment.

## Development Workflow

### Prerequisites
- **Node.js**: ≥ 22.0.0
- **npm**: ≥ 10.0.0
- *(Optional)* **PostgreSQL 17**: Required only if running full database RLS test suite (`npm run test:db`).

### Local Setup
```bash
# Clone your fork
git clone https://github.com/<your-username>/mcda-tools.git
cd mcda-tools

# Install dependencies
npm ci

# Configure environment variables
cp .env.example .env.local
# Edit .env.local with your Supabase credentials (a free Supabase project works)

# Start development server
npm run dev
# Open http://localhost:3000
```

### Running Tests
Before opening a pull request, all test suites must pass:

```bash
# 1. Strict TypeScript check
npm run typecheck

# 2. Mathematical unit tests across all 7 MCDA methods and GIS algorithms
npm test

# 3. Excel export and live formula round-trip tests
npm run test:excel

# 4. Production build check
npm run build
```

## Development Principles & Architecture Rules

1. **Ground Truth Verification**:
   - The platform algorithms are verified against exact mathematical reference values derived from Python's `pyDecision` library and established academic papers (located in [`notebooks/`](notebooks/)).
   - **Never adjust test assertions or reference numbers** simply to make a failing test pass. If you discover a legitimate numerical divergence, document the mathematical justification and reference paper in the pull request.
2. **Formula-Driven Excel Exports**:
   - Workbooks generated by `src/lib/excel.ts` must use **live spreadsheet formulas** (e.g., `SUMPRODUCT`, `INDEX`, power iteration steps, conditional logic), not hardcoded static numbers.
   - Excel workbooks must pass LibreOffice headless recalculation (`npm run test:excel:recalc`).
3. **Privacy by Design**:
   - Never commit sensitive personal data or real expert evaluations. All test data and fixtures must use synthetic, anonymized examples (see `scripts/fixtures/`).
4. **Code Quality and Language**:
   - Code, identifiers, comments, and commit messages should be in English.
   - User-facing text should remain accessible and adhere to established UX patterns.
5. **Transparency & AI Disclosure**:
   - In accordance with academic software transparency guidelines, please state in your pull request description if generative AI tools were used to assist in writing or reviewing code.

## Submitting Pull Requests

1. Fork the repository and create a branch from `main`:
   ```bash
   git checkout -b feature/your-feature-name
   ```
2. Make your changes with clear, descriptive commit messages.
3. Verify that all tests pass (`npm run typecheck`, `npm test`, `npm run test:excel`, `npm run build`).
4. Open a pull request against the `main` branch with a clear summary of what was changed and why.

## Semantic Versioning & Release Protocol

This project strictly adheres to [Semantic Versioning 2.0.0](https://semver.org/):
- **Patch (`0.1.0` → `0.1.1`)**: Backward-compatible bug fixes or calculation refinements.
- **Minor (`0.1.0` → `0.2.0`)**: New decision methods, new GIS layer formats, or significant backward-compatible functionality.
- **Major (`0.X.Y` → `1.0.0`)**: Production-ready stability with guaranteed API and schema compatibility.

### Releasing a New Version
When cutting an official release, the version number and DOI must be synchronized across:
1. `src/lib/version.ts` (`APP_VERSION`, `APP_RELEASE_TAG`, `APP_DOI`)
2. `package.json` (`version`)
3. `CITATION.cff` (`version`, `date-released`, `doi`)
4. `src/lib/citation.ts`
5. `README.md` & `README.es.md` (badges and citation examples)
6. `CHANGELOG.md`

Tag the release commit and push to GitHub:
```bash
git tag -a vX.Y.Z -m "vX.Y.Z - Release summary"
git push origin main
git push origin vX.Y.Z
```
Zenodo will automatically archive the GitHub release and assign a Version DOI linked to the permanent Concept DOI.
